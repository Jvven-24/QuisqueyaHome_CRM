# D21 · Capacidades OSS transversales del CRM

Fecha: 2026-10-04. Productor: D21. Estado: INVESTIGACIÓN, pendiente de revisión independiente D03 y D12 para licencia/seguridad. Alcance: capacidades fuera del motor CRM principal. Evidencia: documentación oficial pública consultada en esta fecha y mapa local `.viltrum/vre-os/MAPA-SISTEMAS-OSS.md`. No se instaló ni conectó ningún producto durante este análisis.

**Lectura de la matriz:** `RUN` = servicio independiente; `APP` = dependencia de la aplicación; `PORT` = código importado selectivamente. `API/UI`: S = funcionalidad expuesta de forma documentada por API para pintar la UI del CRM; P = API genérica o librería exige adaptador, y la cobertura exacta requiere prueba; N = no hay API documentada para esa acción; ? = sin verificar. `Grado`: `instalado` requiere comprobación local, `adaptar` exige integración/configuración, `construir` requiere lógica del CRM y `UNKNOWN` exige una prueba. Una funcionalidad existente en el producto no aparece automáticamente en la interfaz propia.

## Correcciones al mapa local

1. **Corrección de identidad:** `github.com/calcom/cal.com` redirige a [`calcom/cal.diy`](https://github.com/calcom/cal.diy). Cal.com anunció que su edición comercial pasa a código cerrado; [comunicado](https://cal.com/blog/cal-com-goes-closed-source-why) y [changelog v6.4](https://next.cal.com/blog/calcom-v6-4). El fork comunitario Cal.diy declara MIT en su [README](https://github.com/calcom/cal.diy) y [LICENSE](https://github.com/calcom/cal.diy/blob/main/LICENSE), sin EE. Por eso la nota anterior «Cal.com núcleo AGPLv3 + EE» era histórica y **falsa para el repositorio actual**. El README de Cal.diy recomienda estrictamente uso personal no productivo y separa su mantenimiento de la plataforma Cal.com; el documento de instalación describe builds de producción, pero eso no suprime la advertencia ni acredita soporte. Tratar Cal.diy como candidato de PoC local, no como proveedor productivo aprobado. La [documentación API comercial](https://cal.com/docs/api-reference/v2/bookings/decline-a-booking) tampoco acredita comportamiento del fork.
2. Schedule-X básico permite mostrar y gestionar eventos, pero drag-and-drop, resize y resource scheduler son Premium en v4. [Migración oficial](https://schedule-x.dev/docs/calendar/major-version-migrations).
3. Activepieces Community sí permite ejecutar flujos y crear piezas; embedding del constructor, SSO, audit logs y Git Sync son Enterprise. [Community](https://www.activepieces.com/solutions/open-source-developers), [embedding](https://www.activepieces.com/docs/embedding/embed-builder).
4. ZEN Engine es APP, una librería en proceso, no un servidor RUN. El diseñador/gobierno visual de GoRules es otra oferta. [Fuente oficial](https://gorules.io/open-source).
5. Papermark expone REST de documentos, links, datarooms, visitantes y analítica, pero su página oficial aún lista webhooks como planificados. Debe comprobarse que la edición autoalojada fijada trae los mismos endpoints y ajustes. [API oficial](https://docs.papermark.com/docs/api).
6. Frappe Learning importa ZIP de contenido, expresamente no SCORM; si SCORM es requisito, Moodle es la opción documentada. [Frappe](https://docs.frappe.io/learning/create-a-course), [Moodle](https://docs.moodle.org/500/en/images_en/archive/2/2a/20250630145556%21Moodle_features_students.pdf).

## Juicio de cobertura y siguiente prueba

La matriz acredita **capacidades publicadas**, no un porcentaje terminado ni módulos instalados en el CRM. No se calcula un porcentaje hasta fijar una lista de requisitos con peso, edición/versión de cada producto y pruebas API locales. Para una UI propia, las funciones marcadas S o P siguen necesitando autenticación, mapeo de IDs, permisos, traducción, control de errores, pruebas de contrato y operación local. El runtime de mensajería Viltrum se documenta como existente en el mapa local, pero no se volvió a sondear en esta investigación y no se marca `instalado` aquí.

Pruebas acotadas propuestas antes de decidir: (1) seleccionar Moodle frente a Frappe Learning con un curso, matrícula, lectura de progreso y certificado por API; incluir un paquete SCORM si es requisito; (2) validar Papermark autoalojado con subir documento, link, visita y analítica; (3) evaluar booking público **Cal.diy** y su correlación con lead, fijando commit y probando mantenimiento, seguridad y API v2 propia; (4) evaluar reglas ZEN para comisión y plan de pagos con casos dorados; (5) confirmar alcance DGII/e-CF por separado con D12/D03. Se ejecutan en local cuando las dependencias sean autorizadas y preparadas; este expediente no inicia instalaciones.
