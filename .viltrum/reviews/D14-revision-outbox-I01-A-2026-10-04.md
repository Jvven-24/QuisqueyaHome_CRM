## Bloqueos para subficha READY

1. **Ficha formal ausente.** Crear I01-A con `estado: REVIEW` y sus criterios/salida; revisar en D03/D11/D12/D14 antes de `READY`. El plan L1 no reemplaza una ficha. Su lote debe tener archivos cerrados y mecanismo de revisión independiente.
2. **Oráculo DB para ausencia de transacción durante red.** El test propuesto «otro agregado progresa» no basta: `SKIP LOCKED` permite ese progreso aun si el primer worker conserva transacción y lock. Mientras el stub HTTP esté suspendido, consultar `pg_stat_activity`/`pg_locks` o instrumentar el pool para demostrar que la conexión del claim volvió a estado sin transacción antes de invocar el puerto; después probar claim de otra entidad. Evitar depender de una duración arbitraria.
3. **Fencing exhaustivo.** Declarar campos y predicados exactos de `reclamar`, `confirmarEnviado` y `confirmarFallo`; ambos finales, inserción de DLQ y upsert de `external_refs` deben ser condicionales al token vigente en una transacción breve. Probar dos carreras: vencimiento + segundo claim + éxito tardío primero; vencimiento + segundo claim + fallo tardío primero. Ningún final obsoleto modifica referencias, intentos, historial ni DLQ.
4. **Orden y eventos heredados.** D11/D03 deben fijar cómo nace la revisión monotónica, el `destination` y el orden por entidad. Eventos previos sin revisión no se envían por intuición; definir migración/backfill o reconciliación sin perder historial. Incluir la política de bloqueo/desbloqueo del agregado si revisión anterior cae a DLQ. «Perdido» es resultado archivado y no séptima etapa activa al emitir negocio.
5. **Éxito remoto incierto.** La garantía de deduplicación de Twenty sigue desconocida. Para READY de **I01-A aislada**, no hace falta certificar Twenty, pero sí especificar que timeout/caída tras enviar nunca dispara automáticamente una operación externa duplicable. El test de DB prueba identidad y estado `HUMAN_REQUIRED`/reconciliación; la integración I01-B/C permanece bloqueada hasta verificar el método remoto por versión.
6. **Fallos y permisos medibles.** Escribir tabla por fallo con resultado exacto y límite de intentos. Probar que usuario SQL ordinario no lee/modifica cola, que worker puede claim/finalizar con privilegio mínimo, y que la migración activa RLS. La presencia de `.enableRLS()` no demuestra políticas/privilegios efectivos.
7. **Gate técnico actual.** Línea base: `typecheck` verde, 512/512 pruebas unitarias, 130/130 DB; `lint` rojo por `capture_b.cjs` y `spec:check` rojo con 0 READY. ## Protocolo DB mínimo propuesto para I01-A

Usar `scripts/test-db/run.mjs` sobre DB efímera para las carreras; no tocar datos reales de desarrollo. Barreras explícitas entre promesas/conexiones sustituyen pausas temporales. Registrar conteos y filas finales (sin payload/PII) por `event_id` y `command_id`:

1. Dos transacciones emiten el mismo comando/payload; exactamente una fila y una revisión. Clave igual/payload diferente da conflicto; rollback del cambio de negocio elimina su evento.
2. Workers W1/W2 reclaman simultáneamente; un solo token para el evento. W1 queda en puerto HTTP pendiente; no hay transacción/lock de W1 abierta en PostgreSQL. W2 procesa otro agregado.
3. Vence lease de W1 mientras su puerto sigue pendiente; W2 reclama con token nuevo. Al acabar W1, `confirmarEnviado` y `confirmarFallo` obsoletos afectan cero filas y no cambian refs/DLQ/historia. Se prueba cada final en caso separado.
4. Revisiones r1/r2 del mismo negocio y r1 de otro: r2 espera r1; el otro progresa; una confirmación tardía de r1 no pisa r2. Repetir con r1 agotado/DLQ según política definida.
5. Se corta conexión/proceso después del claim, luego después de éxito remoto y antes del final local; worker nuevo usa la misma DB, recupera lease y conserva identidad/revisión. Resultado externo desconocido queda para conciliación, no para reemisión ciega.
6. 401/403/404/409/429/5xx/timeout y respuesta inválida se inyectan en adaptador simulado; para cada uno se comprueba clase, intentos, disponible/dead, `Retry-After` y clave. Ningún fallo cambia entidad canónica.
7. Rol SQL sin autorización recibe denegación; worker de mínimo privilegio reclama/finaliza. Migración temporal y `DEV COUNTS PASS` deben quedar en salida.
