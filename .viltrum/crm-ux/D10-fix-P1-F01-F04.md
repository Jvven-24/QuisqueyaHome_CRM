## Cambios

### F01 · SSRF de despacho webhook

- `src/infrastructure/comunicaciones/proveedor-despacho.ts:166`: el destinatario debe coincidir con una URL HTTPS exacta registrada en servidor. Registro ausente, inválido o no coincidente falla cerrado. No se admite usuario/contraseña en URL, fragmento, HTTP ni puerto distinto de 443.
- `src/infrastructure/comunicaciones/proveedor-despacho.ts:172`: resolución previa de todas las direcciones; se rechaza el destino si alguna dirección es interna, loopback, link-local, reservada o de documentación/transición conforme a la política conservadora. Se validan también IP literales normalizadas, incluidas variantes ofuscadas y IPv4 mapeada en IPv6.
- `src/infrastructure/comunicaciones/proveedor-despacho.ts:187`: HTTPS nativo con `agent:false` y `lookup` fijado a una IP ya validada, conservando el hostname de URL y la verificación TLS predeterminada. Evita una segunda resolución susceptible de rebinding y reutilización de sockets de otra resolución. No sigue redirects: 3xx se considera fallo.
- Timeout de 10 segundos compartido entre resolución y solicitud. Se devuelve un error genérico ante fallo, sin reflejar detalles externos. Se descarta el cuerpo de respuesta externo.
- `src/infrastructure/env.ts:59`: contrato central de configuración, registro de destinos como array JSON de URLs y timeout. Las lecturas de configuración de Telegram/WhatsApp del mismo adaptador se trasladaron aquí, conservando su comportamiento.
- `src/infrastructure/comunicaciones/proveedor-despacho.test.ts`: nueve pruebas con transporte/resolución aislados; registro cerrado, restricciones URL/IP, DNS mixto, IP ofuscada, conexión fijada, redirects, abort durante DNS/transporte y errores sanitizados.

Decisión de compatibilidad: se conserva el destinatario URL existente, restringido a entradas registradas exactas. Un identificador de integración requeriría cambiar el contrato consumidor y no se introdujo. **Sin registro servidor, webhook deja de despachar**. Ningún destino real fue inventado o configurado. La política rechaza también algunos rangos especiales públicos para fallar hacia lo restrictivo.

Se reutilizaron APIs nativas de Node y el contrato existente de despacho, sin dependencia nueva. Referencias de diseño: [Node HTTPS](https://nodejs.org/api/https.html) y [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html); justifican restringir destinos y controlar resolución, redirects y límites de tiempo. Su consulta no constituye prueba de red/TLS real.
